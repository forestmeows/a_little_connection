To change this, start here

  • Companion labels or request form: public/index.html; actions in public/app.js.
  • Three-in-eight rule or cooldown: server/rules.js, especially consumeUserCue(). Check tests/rules.test.js.
  • Cue definitions and adjustment guidance: server/prompts.js. Unadjusted generation omits app behavior instructions in server/gemini.js.
  • User messaging layout: public/messages.html, public/messages.js, and public/messages.css.
  • Volunteer availability and acceptance: server/routes.js paths /api/volunteer/accept and /api/volunteer/message; interface in public/volunteer.js.
  • Fictional community details: public/groups.json. Bookmark UI is renderGroups() in public/app.js.
A practice to reuse

Specify an observable result before building. Here, “availability must be on to accept or reply” became explicit server checks and a test named availability and explicit acceptance are required for new volunteer replies in tests/volunteer.test.js. A disabled button alone would not establish the rule. On another project, connect the desired behavior to its enforcing code and one meaningful verification.

Also distinguish what tests establish: tests/journey.test.js verifies the app flow with controlled labels. Live Gemini examples check integration and sample behavior, not real-world detection accuracy.

Run it again

In the project terminal run npm start, then open the user app and the volunteer view. The user inbox is /messages. Stop the terminal process with Ctrl+C.

Use npm test for the offline tests. npm run check:gemini makes live model calls and consumes API quota. Keep the key in ignored .env; never show it in a recording or commit it.

This guide is standalone HTML with no scripts, downloads, analytics, or network dependency. The local app links work only while its server is running.
