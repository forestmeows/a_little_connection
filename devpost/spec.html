Follow one turn through the system

Open each step to see the behavior, implementation location, and proof.

1 · Open and activate

public/app.js opens the companion and reads saved settings. Monitoring starts off for first use; activation explains monitoring and automatic guidance. The saved on/off choice survives reopening.

PRD: Activation and Returning Use. Check: saved human history and groups remain after reopen; turning off stops detection and guidance.

2 · Classify a user message, then count

server/gemini.js asks Gemini for allowed cue categories in context. server/rules.js counts each qualifying user message once. Three qualifying messages spanning two categories trigger immediately, even before eight messages.

Trigger at message 5 → skip user messages 6–13 → resume fresh at 14. Invalid classification shows monitoring unavailable; it is not interpreted as a clean result.

PRD: Pattern Detection and Check-In. Check: deterministic threshold/cooldown tests plus a live check of the agreed ordinary/concerning examples.

3 · Generate and inspect a chatbot reply

server/prompts.js adds balanced guidance if manually enabled, accepted, or triggered. User-pattern guidance starts before the next generated reply. Gemini then separately classifies the reply.

One clearly qualifying reply offers an adjustment at most once per AI conversation. Declining does not disable existing automatic guidance. New AI chats reset cues, cooldown, offers, and triggered/accepted guidance; manual guidance remains while monitoring is on.

PRD: Automatic Balanced Responses; Chatbot Reply Flags and User Choice. Check: visible disclosure and independently evaluated positive/negative reply examples. Never manufacture harmful live behavior to make the demo trigger.

4 · Send a request to a real volunteer

server/routes.js saves only the user's written human-chat message. public/volunteer.js displays pending requests and lets one adult set availability and reply.

The views check for local updates about every two seconds. This polling uses no Gemini quota. Offline requests stay pending; no response-time promise or endless waiting screen.

PRD: Volunteer Request and Conversation. Check: a real second person sends a reply that appears in the user window; AI history is absent from volunteer data.

5 · Explore and save communities

public/groups.json holds clearly fictional group descriptions, organizers, joining/contact details, and next sessions with timezones. Bookmarks save group IDs in data/demo.json.

PRD: Interest Groups and Bookmarks. Check: saving does not create duplicate entries or imply membership; bookmarks survive restart.

How we start it

  1. During build, create an eligible free-tier Gemini key and keep it in ignored .env.
  2. Run npm install, then npm start.
  3. Open http://127.0.0.1:3000/.
  4. Open http://127.0.0.1:3000/volunteer in a second window.

Node 24.22.1 is already installed. Slice 1 adapter/setup script is implemented. The live check passed generation and 12 fictional classification fixtures; the browser app is not built yet.

Keep the demo honest

Only consenting adult participants and fictional chat content. No paid billing or paid fallback. No real nonprofit partnership, production accounts, diagnosis, or guarantee of wellbeing benefits.

Record the working journey and provide the public repository. Deployment is optional and not planned.

What must be checked early

Gemini account eligibility, free-tier quota, access to the planned gemini-3.5-flash-lite model, SDK request/JSON-output compatibility, latency, and classification behavior. A monitored turn may use three calls. Quota exhaustion must show an error, never silently switch to a paid model or scripted reply.

Slice 1 evidence: SDK 2.31.0 installed; live generation and all 12 fictional fixtures passed once, plus five offline adapter tests. Interactions uses labeled JSON-string input and explicit response_format/schema. The main remaining risk is semantic classification accuracy and free-tier capacity. The exact threshold/cooldown logic can be verified separately from the model.

Files and boundaries

public/: screens and styles. server/: routes, rules, model calls, prompts, persistence. data/demo.json: ignored runtime history. tests/: meaningful rule, persistence, handoff tests and fictional fixtures. devpost/: planning documents.

The full annotated file tree, data fields, endpoint contracts, failures, and verification steps are in the canonical Markdown spec.

Local server binds only to this laptop; no production authentication is implied. Serialized file writes avoid lost messages. Failed sends retain unsent text and allow retry without double-counting.
